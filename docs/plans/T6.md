## 3. Kill attribution (SPEC 3.1)

### 3.1 Events [V]
- `ServerLivingEntityEvents.AFTER_DAMAGE (LivingEntity e, DamageSource src, float base, float taken, boolean blocked)`. Fabric injects it at `TAIL` of `LivingEntity.hurtServer`. It does not fire when `hurtServer` returns early (invulnerable, cancelled).
- `ServerLivingEntityEvents.AFTER_DEATH (LivingEntity e, DamageSource src)`. Fabric injects it in `LivingEntity.die`.
- Order: `hurtServer` calls `die` before its `TAIL`. Thus for the killing hit, `AFTER_DEATH` comes **before** `AFTER_DAMAGE`. Do not rely on the ledger for the killing hit. Resolve the killing `DamageSource` directly first.

### 3.2 `resolvePlayer(DamageSource)` — who is responsible for one hit
1. `Entity c = src.getEntity()` (causing entity). For arrows, tridents, thrown items, fireworks, `source(type, direct, causing)` sets `causing` = shooter. [V] `DamageSources.arrow` bytecode.
2. If `c` is a `ServerPlayer`: return it.
3. If `c` is an `OwnableEntity` (tamed wolf, cat, parrot, ...): use `getRootOwner()` [V]. If it is a `ServerPlayer`: return it.
4. If `c` is a `TraceableEntity` (TNT, evoker fangs, ...): use `getOwner()` [V] and repeat steps 2–4. Max depth 4 (no loop).
5. Else: none.
- Ignore spectators and players without a team.

Vanilla `lastHurtByPlayer` is not enough: it keeps the player for 100 ticks (5 s) only and knows only tamed wolves [V] (`LivingEntity.resolvePlayerResponsibleForDamage`). Thus we keep our own tracker.

### 3.3 10 s last-hit rule (`LastHitTracker`)
```java
final class LastHitTracker<V, P> {           // V = victim UUID, P = player UUID
  LastHitTracker(long windowTicks);          // 200 = 10 s
  void record(V victim, P player, long tick); // newest hit wins
  Optional<P> lookup(V victim, long now);     // empty if now - tick > window
  void forget(V victim);
  void prune(long now);                       // remove old entries
  void clear();
  int size();
}
```
- `AFTER_DAMAGE`: if phase is `PREP` and `resolvePlayer(src)` gives a team player, `record(victim.getUUID(), player.getUUID(), now)`. Record also when `taken == 0` but `!blocked` (a hit counts). Do not record when `blocked`.
- `now` = `server.getTickCount()` [V]. Server ticks, not wall clock.
- Prune every 200 ticks in `END_SERVER_TICK`. Clear on `PREP.onExit`.
- The window is inclusive: a hit at tick T counts for a death at tick T+200, not T+201.

### 3.4 On death (`AFTER_DEATH`)
```
if phase != PREP: return
if !MobEligibility.counts(victim, blacklist): return
killer = resolvePlayer(src)                          // direct, projectile, pet
if killer == null: killer = tracker.lookup(victim, now)  // trap, fall, fire, lava, other mob, /kill
tracker.forget(victim)
if killer == null or no team: return
pool(team).add(id); killer.sendOverlayMessage("+1 <name> (total <n>)")
```
- `MobEligibility.counts`: `!(e instanceof Player)`, id not in blacklist, `SpawnEggItem.byId(e.getType()).isPresent()` [V]. Id = `EntityType.getKey(type).toString()` [V], for example `minecraft:zombie`.
- The 26.3 item registry has 88 spawn eggs [V]. Wither, iron golem, snow golem, copper golem have eggs. Ender dragon has an egg too, thus it must stay on the blacklist.
- Babies: same `EntityType`, so they count as the same type. No extra code.
- Slime / magma cube: each slime dies once, so each counts once. No extra code.
- Action bar: `ServerPlayer.sendOverlayMessage(Component)` [V]. Name: `type.getDescription()` [V] (translatable, so the client shows its own language). `total` = count of this type in the team pool (see open question Q1).
- Only the killer sees the message. The enemy team never gets pool data.

## 4. MobPool
- Key type: `String` entity id. Thus `MobPool` and `WaveSetup` need no Minecraft bootstrap in unit tests.
- Order: sorted by id (`TreeMap`). The order must not change when counts change. Then eggs do not jump in the menu.
- Memory only (in `GameContext`). A server restart ends the game. The pool is not in the save data (SPEC does not ask for it).

## 5. WaveSetup (pure logic)

### 5.1 API
```java
public final class WaveSetup {
  public static final int WAVES = 3;              // waves are 1..3
  public WaveSetup(Map<String, Integer> pool);    // copies; ignores counts <= 0
  public SortedMap<String,Integer> pool();        // immutable view, no 0 entries
  public SortedMap<String,Integer> wave(int w);   // immutable view, no 0 entries
  public int poolCount(String id);
  public int waveCount(int w, String id);
  public int poolTotal();
  public int waveTotal(int w);
  public int toWave(String id, int w, int amount);   // returns moved count, clamps to available
  public int toPool(int w, String id, int amount);   // returns moved count, clamps to available
  public void finish();                              // all pool mobs -> wave 3; pool is empty after
  public boolean finished();                         // after finish(), all moves throw IllegalStateException
  public long version();                             // +1 on each real change (moved > 0)
  public List<SortedMap<String,Integer>> snapshot(); // 3 immutable maps
}
```
- Invariant: for each id, `pool + wave1 + wave2 + wave3` = start count. Unit test this after random moves.
- `amount <= 0`, unknown id, or wave not in 1..3: `IllegalArgumentException` for bad wave, return 0 for the rest.
- `Integer.MAX_VALUE` as amount means "all".

### 5.2 `MoveAmount`
```java
static int of(boolean left, boolean right, boolean shift); // 0 = no action
```
| Click | Amount |
|---|---|
| left | 1 |
| shift + left | 10 |
| right (with or without shift) | `Integer.MAX_VALUE` (all) |
| all other (middle, number key, drop, drag, double click, offhand swap) | 0 |

The GUI maps sgui `ClickType` [V: fields `isLeft`, `isRight`, `shift`, `isDragging`, `numKey`] to these booleans. Drag and number-key clicks give 0.

## 7. Live update for many viewers
- `WaveConfigHub` (one per team, in `GameContext`): `Set<WaveConfigGui> open`, `boolean dirty`.
- Open: `new WaveConfigGui(...)`, `open()`, add to `open`. Remove in `onRemoved()` [V: `GuiLike.onRemoved`, `onPlayerClose(boolean)`].
- Click: change `WaveSetup`. If `moved > 0`, set `dirty = true`. Re-render only the clicking GUI at once (fast feedback for the clicker).
- `ServerTickEvents.END_SERVER_TICK`: for each dirty hub, call `render()` on each open GUI, then `dirty = false`. Thus 20 clicks in one tick give 1 refresh per viewer, not 20.
- Each viewer has its own view state (wave tab, pages). The model is shared. Different viewers can look at different waves.
- Time slot (32) and ready slot (33): update once per second (every 20 ticks) for all open GUIs, also when not dirty.
- `render()` sets all 54 slots. sgui sends only slots that change [U]. 54 slots × few players per tick is cheap; no more optimization.
- Ready change (`/ma ready` or slot 33): mark the hubs of **both** teams dirty (the ready count shows to all).
- `WAVE_CONFIG.onExit`: close all GUIs (`close()`), clear the hubs. Then call `finish()`.
- Player disconnect: sgui calls `onRemoved` [U]. Also remove GUIs of a player in `ServerPlayerEvents.LEAVE` [V] to be safe.

## 8. Commands and ready
- `/ma waves` (perm 0): only in `WAVE_CONFIG`, only for team players. Else a red error message.
- `/ma ready` (perm 0): toggles the player in `READY` (a `Set<UUID>`). Message to all game players: `<name> is ready (x/y)`. When all **online** team players of both teams are ready: `GameManager.endPhaseNow()`.
- Re-check "all ready" also on `LEAVE` (a player that leaves can make the rest complete).
- Menu item (`WaveMenuItem`): at `WAVE_CONFIG.onEnter` put a `minecraft:recovery_compass` with custom name "Wave menu" and custom data `mobarena:wave_menu` [V: `DataComponents.CUSTOM_DATA`] in hotbar slot 9 (`Inventory` index 8). If the slot is not empty, move the old stack to `getFreeSlot()` [V]; if no free slot, put it in the team backpack, else skip the item and tell the player to use `/ma waves` (Q4). Open with `UseItemCallback.EVENT` [V in TECH]. At `onExit` remove all stacks with this tag from all team players.

`MobPoolTest`

2. `add` twice same id → count 2; different ids are independent.
3. `snapshot()` is sorted by id and immutable (modify → exception); later `add` does not change an old snapshot.

`LastHitTrackerTest`
4. Hit at tick 100, lookup at 300 → present (inclusive window 200).
5. Hit at 100, lookup at 301 → empty.
6. Two players hit; newest hit wins.
7. `forget` removes; `prune(now)` removes only old entries (`size()` check).

`WaveSetupTest`
8. Constructor ignores 0 and negative counts; copies the input map (input change has no effect).
9. `toWave` 1 / 10 / all: correct counts; clamps when fewer are available; returns moved count.
10. `toWave` with unknown id → 0, version does not change.
11. `toPool` back, same rules; entry with 0 disappears from `pool()` / `wave()`.
12. Bad wave (0, 4) → `IllegalArgumentException`.
13. `finish()`: pool to wave 3, keeps existing wave 3 counts (adds), pool empty; moves after finish → `IllegalStateException`.
14. `finish()` with empty waves 1 and 2 → allowed (empty wave = cleared at once in T7).
15. Invariant: 1000 random moves with a fixed seed → per id sum is unchanged, no negative count.
16. `version()` increases only on real changes.
17. `snapshot()` returns 3 immutable maps.

`MoveAmountTest`
18. left → 1, shift+left → 10, right → MAX, shift+right → MAX, none → 0.

## 10. Open questions (for orchestrator)
- **Q1** Action bar `(total 14)`: total of this mob type, or total of all mobs in the pool? Plan: total of this type.
- **Q2** SPEC 3.1: does the 10 s rule also apply to projectile and pet kills? Plan: no. Projectile/pet kills always count. The 10 s rule is only for kills with no responsible player (trap, fall, fire, lava, other mob, `/kill`).
- **Q3** Kill by another mob (for example a skeleton shoots a zombie) after a team player hit in the last 10 s: count it? Plan: yes (same as a trap).
- **Q4** Hotbar slot 9 is full (keep inventory): plan moves the old stack to a free slot, then to the backpack, else no item. OK? Must the menu item have a drop/move guard like the backpack (T4)? Plan: reuse the T4 guard if T4 makes it generic; else only remove it at phase end.
- **Q5** `/ma ready`: SPEC 6 says "all players of both teams"; SPEC 10 says "mark the team as ready". Plan: per player, all online players of both teams. Toggle (a second `/ma ready` cancels).
- **Q6** Who teleports players to the holding area in `WAVE_CONFIG`? Not T6 scope. Plan: T5 or T2. Please assign.
- **Q7** Does a kill count only in the killer's own team world? Plan: no world check, only phase `PREP` + killer team. In `PREP` a player can only be in the own team worlds.
- **Q8** Must the pool survive a server restart (save data like the backpack)? Plan: no, memory only.
