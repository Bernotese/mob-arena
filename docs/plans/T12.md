## T12b plan: dead players across phase changes (bug 1, High)

### Cause (verified in 26.3 bytecode)
- A player on the death screen has health 0. `LivingEntity.tickDeath` removes the entity (`RemovalReason.KILLED`) after 20 ticks. The entity stays in the `PlayerList` until the client sends `PERFORM_RESPAWN`.
- `ServerPlayer.teleport(TeleportTransition)` returns `null` at once when `isRemoved()`. `teleportTo(...)` calls it too. Every phase teleport therefore does nothing for that player. The listed teleports are `LobbyManager.sendToLobby` (WAVE_CONFIG, LOBBY), `ArenaBattle.placeAtSpawn` (arena ready, sudden death `resetPlayers`, `ArenaBattles.end`) and `ArenaBattles.spectate`.
- `ArenaBattles.alive()` needs `player.isAlive()`, so it is false. `allDown()` is then true at arena tick 1, and the team gets ALL_DOWN.
- `ServerGamePacketListenerImpl.handleClientCommand(PERFORM_RESPAWN)` returns without action when `getHealth() > 0`. Do not "heal" a dead player (`setHealth`) to fix this. The client then stays on the death screen, because the server ignores the Respawn click.
- After LOBBY the level is deleted. The client clicks Respawn later. Then `RespawnRouter.route` gets `ctx == null` and returns empty, so vanilla puts the player at the world spawn. Until the click, the client shows the deleted level (screenshot 5).

### Decision: force the vanilla respawn on the server
Options:
1. Force the respawn at phase changes, at join, and while ARENA or SUDDEN_DEATH runs. **Chosen.**
2. Queue the move until the player clicks Respawn. Rejected: the ALL_DOWN problem stays, the level can be deleted before the click, and an AFK player blocks the fix.
3. Use immediate respawn (gamerule) in game levels. Rejected: game rules are not per level, the death screen in PREP is wanted, and it does not fix players that were offline.

How: call the vanilla path `player.connection.handleClientCommand(new ServerboundClientCommandPacket(Action.PERFORM_RESPAWN))` on the server thread. `PacketUtils.ensureRunningOnSameThread` passes on the server thread. This path calls `PlayerList.respawn(player, false, KILLED)` and sets `connection.player` to the new entity. It also runs `resetPosition()` and `restartClientLoadTimerAfterRespawn()`, and fires `ServerPlayerEvents.AFTER_RESPAWN`. Do not call `PlayerList.respawn` directly: then `connection.player` keeps the old entity.
The respawn makes a **new `ServerPlayer` object**. After a revive, code must get the player again with `server.getPlayerList().getPlayer(uuid)` or `connection.player`.

### Changes
1. **New `src/main/java/dev/mobarena/core/DeadPlayers.java`** (server thread only):
   - `static ServerPlayer revive(ServerPlayer player)`: if `player.isDeadOrDying()` and `player.connection != null` and `PlayerList.getPlayer(uuid) == player`, call `player.connection.handleClientCommand(new ServerboundClientCommandPacket(PERFORM_RESPAWN))` in try/catch (log the error). Return `player.connection.player` (the new entity), or the same player if nothing happened.
   - `static void reviveTeamPlayers(GameContext ctx)`: for a copy of `ctx.server().getPlayerList().getPlayers()`, call `revive(p)` for each player with `ctx.team(p.getUUID()) != null && p.isDeadOrDying()`. Lobby players without a team are not changed.
   - Do not check `wonGame`. The team End exit portal does not start the credits, because the dimension key is `mobarena:*` and not `Level.END`.
2. **`core/GameManager.transition(Phase next)`**: after `context.timer().reset(...)` and before `notifyListeners("enter", ...)`, add `if (context.server() != null) DeadPlayers.reviveTeamPlayers(context);`.
   - The new phase is already set, so `RespawnRouter` uses the new phase. The `onEnter` listeners then see only living entities and move them as normal: WAVE_CONFIG and LOBBY use `sendToLobby`, ARENA uses the arena-ready `placeAtSpawn`, SUDDEN_DEATH uses `resetPlayers`.
   - Unit tests have no server (`server() == null`), so they are not changed.
   - This also fixes the first wrong step of the repro (PREP -> WAVE_CONFIG). The player is then alive in the lobby and cannot die in WAVE_CONFIG (lobby protection).
3. **`arena/ArenaBattles.tick()`**: before the battle loop, revive each dead online team player (`for team, onlinePlayers(team)`, `isDeadOrDying()` -> `DeadPlayers.revive`). In ARENA and SUDDEN_DEATH, a vanilla death is normally cancelled by `ALLOW_DEATH`. It can still happen with a battle in WAITING_ARENA or ELIMINATED, a death outside the own arena level, or a mixin edge case. The existing ARENA/SD `RespawnRouter` hook and the `AFTER_RESPAWN` -> `group.rejoin` hook then put the player into the respawn timer (or spectate when ELIMINATED). Do not change `alive()`: after this change it sees no dead entity for more than 1 tick.
4. **`world/RespawnRouter`**: register an END hook in `ArenaModule.init` (in the same loop, or separately) that returns the own arena team spawn. Arenas still exist in END and are deleted in LOBBY. Without it, a revive at END entry uses the vanilla world spawn or a team bed. Do not change `accepts()`: T12a owns it. T12b must work with the old and the new `accepts()`.
5. **Join of a player who logged out dead** (`MobArena.onInitialize`): register a `ServerPlayConnectionEvents.JOIN` handler `DeadPlayers.revive(handler.player)` **before** the module `init` lines. Fabric calls JOIN handlers in registration order, and Backpack, Wave, Hud and Lobby must see the new entity. They read `handler.player` when they are called, and that is the new entity. Revive all dead joiners, also when no game runs: the lobby is always the target, and `sendToLobby` cannot move a dead player.
6. **`core/LobbyManager.leave`**: do not store a `ReturnPosition` for a player with `isDeadOrDying()`. That position is the death position (for example the End void). **`world/WorldModule` DISCONNECT**: do not call `rememberPrepReturn` for a dead player. Then the PREP rejoin hook sends the player to `prepSpawn`.
7. No change to `ArenaBattles.alive()`, `RespawnManager`, `ArenaBattle.placeAtSpawn`. They are correct for living entities.

Order check for a PREP death that continues to ARENA (1v1): the death happens in PREP. At the PREP -> WAVE_CONFIG revive, `route` uses phase WAVE_CONFIG (no hook) and gives the vanilla position. `LobbyManager.onEnter(WAVE_CONFIG)` then calls `sendToLobby`, the same as for all players. At ARENA the player is alive and is moved at arena ready. There is no ALL_DOWN.

### Risks
- Calling `handleClientCommand` directly is a small coupling to vanilla internals. It is the only path that also updates `connection.player`. A mixin accessor for `ServerGamePacketListenerImpl.player` with `PlayerList.respawn` is the fallback.
- Code that keeps `ServerPlayer` objects across a phase change gets stale objects. Known holders: HUD boss bars (`AFTER_RESPAWN` handler exists) and wave menu sessions (WAVE_CONFIG opens them after the revive). Search for `Map<.*ServerPlayer` and `List<ServerPlayer>` fields in the implementation.
