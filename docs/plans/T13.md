## T13a plan: duplicate player entity after a rejoin (bug 1, High)

### Cause (verified: 26.3 bytecode and a probe GameTest)
- Fabric `ServerPlayConnectionEvents.JOIN` fires **inside** `PlayerList.placeNewPlayer`. `fabric-networking-api-v1` `PlayerListMixin` injects at `new ClientboundPlayerAbilitiesPacket(...)`. Vanilla order in `placeNewPlayer`:
  1. `ServerLevel level = player.level()` (stored in a local variable; this is the level the player was loaded into)
  2. login packets, abilities packet: **Fabric JOIN is fired here**
  3. `players.add`, `playersByUUID.put`
  4. `level.addNewPlayer(player)`: it uses the stored local `level`
- Our `MobArena` JOIN handler calls `lobby.join(player)`. In ARENA that calls `player.teleportTo(arenaLevel, ...)` (`LobbyManager.join` else branch, then `ArenaBattles.rejoin` -> `RespawnManager.down`). The teleport across levels adds the entity to the arena level and sets `player.level()` to the arena. Then vanilla step 4 adds the **same entity** to the old level (`world`) too. The entity is now registered in 2 levels.
- Probe result (main 5407ed8, the PREP disconnect is alive). At rejoin in ARENA, `minecraft:overworld entity=SAME inPlayers=true | red_arena entity=SAME inPlayers=true`. After `game.stop()` the player is in the overworld, but the red arena still has the entity in its player list. In the real game the next level change finds the old UUID entry ('Force-added player with duplicate UUID', 'UUID of added entity already exists ... removed=DISCARDED'). The client then stays in the deleted arena.
- T12b is not the cause: `DeadPlayers.prepareJoin` changes only fields (health, food, effects). The same bug happens for an alive player (the probe used an alive player). The bug existed before T12b. Each cross-level teleport in our early JOIN path causes it: ARENA, SUDDEN_DEATH and END rejoin into the arena, and WAVE_CONFIG/LOBBY `sendToLobby` when the saved level is not the overworld. A PREP return to the same level does not cause it, because there is no level change.
- The T12b rejoin GameTests (`deadDisconnectRejoinsInArena` ...) use the real `placeNewPlayer`, so they had the bug. They check only `PlayerList.getPlayer(uuid)`, not the level registration, so they passed.

### Fix
1. **`MobArena.onInitialize`**: move the routing handler from `ServerPlayConnectionEvents.JOIN` to `net.fabricmc.fabric.api.entity.event.v1.ServerPlayerEvents.JOIN` (fabric-entity-events-v1 `PlayerListMixin`, `placeNewPlayer` at **RETURN**, after `addNewPlayer`):
   ```java
   ServerPlayerEvents.JOIN.register(player -> {
       TeamManager.get().sync(player);
       lobby.join(player);
   });
   ```
   `lobby.join` runs all rejoin hooks (WorldModule PREP routing, ArenaBattles.rejoin). They all move to the safe point.
   **Prototype verified:** with only this change, the probe shows one registration (red arena after rejoin, overworld after stop), and all 145 required GameTests pass.
2. Keep `DeadPlayers.prepareJoin` on the early `ServerPlayConnectionEvents.JOIN`. It must run before the first health sync, and it does not change the level. Correct its comment: "Fabric JOIN fires inside placeNewPlayer, before the player is in the PlayerList and in its level. Do not teleport here."
3. Keep the other early JOIN handlers (Backpack `removeBackpacks`, Wave `items.remove`, Hud `hud.add`). They change only inventory and boss bars, not the level. Add a short comment at `MobArena` for the next developer: "Level changes on join only in ServerPlayerEvents.JOIN."
4. Optional guard in `LobbyManager.join`: log a warning if `player.level().getEntity(player.getUUID()) != player` before the teleport. Then a future early call is visible in the log. No behavior change.
